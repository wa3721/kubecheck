1 概述Introduction

kubectl-check 是什么、解决什么问题、不做什么。

kubectl-check 是一个 kubectl 插件，用于 Deployment 发布（rollout）后的自动化校验：定位本次发布的目标 Pod，按两级独立超时校验 Pod 就绪状态与 容器日志，异常时发送告警（优先飞书，未配置降级控制台），并以标准化退出码结束——可直接嵌入 CICD 流水线做发布卡点。

设计边界（先读这段，避免误解）

  • 只监视，不操作：不执行任何回滚、重启、扩缩容等变更动作。
  • 仅校验 Pod 层级：不校验 Deployment 滚动状态与收敛，无整体超时；--pod-ready-timeout（就绪）与 --log-check-timeout（日志）两段超时彼此独立。
  • 目标 = 最新 ReplicaSet 的 Pod：发布刚触发、新 RS 的 Pod 尚未创建时，会在就绪超时窗口内等待目标 Pod 出现（Pending 即算定位成功）。
  • 日志内容判定默认全部关闭：--keyword-check（关键字命中）与 --llm-enable（LLM 仲裁）均需显式开启；关闭时不影响退出检测与就绪校验。
环境要求 本地需有可用的 kubeconfig（遵循 client-go 默认加载规则，支持 KUBECONFIG 环境变量）；工具以当前 kubeconfig 身份访问集群，权限需求与 kubectl get pods / logs 相当。

2 核心特性Features

一览全部能力，点击对应章节可查看详细说明。

🎯目标定位（仅 Pod 层级）

启动即定位最新 RS 的目标 Pod（含 Pending，未出现则等待）；replicas=0 或窗口内未出现 → 告警后退出（码 2）。

⏱️两级独立超时

--pod-ready-timeout 管 Pod 就绪，--log-check-timeout 管日志跟踪，互不挤占、无整体超时。

🩺就绪探针校验

阶段2 等待 Pod Ready 条件（等价 kubectl wait --for=condition=ready）；无探针容器 Running 即视为就绪。

📜实时日志观察

Pod 首次 Running 即启动日志 follow（不等 Ready），与就绪等待并行；--log-console 默认把日志逐行实时输出到控制台（效果同 kubectl logs --follow）。

🔑错误关键字命中

--keyword-check 开启后按 --log-err-keywords 判定错误行；--log-ignore-keywords 抵消无害命中。

🤖LLM 日志错误仲裁

--llm-enable 开启后，命中关键字的日志行交 LLM 批量判定真伪（攒批 + 去重），只有真错误才提醒/落盘；失败降级、连续失败熔断。

💾错误日志落盘

--log-dump 开启后，命中真错误或容器异常退出时写 {namespace}-{pod}-{date}.log，错误行 ANSI 红色标注；两条落盘路径（LLM 全量快照 / 关键字增量追加）。

🛡️防误报设计

controller 删除中（Terminating）的 Pod 不计为异常；忽略关键字命中的行不参与判定与标红；同一故障仅一条告警。

📣飞书告警

优先飞书 interactive 卡片（HMAC-SHA256 签名、非阻塞发送、去重窗口）；未配置 Webhook 自动降级控制台，告警事件不静默丢弃。

🚨容器退出检测

容器异常退出（退出码 ≠ 0）不经仲裁、不受任何开关影响；Ready 前崩溃立即告警，不等就绪超时。

👁️监听模式（常驻）

-A 监听全部命名空间，或 -n 过滤（多值 / * ? 通配）；Deployment 创建或更新（generation 递增）时自动触发检查，存量不触发。

🤚优雅中断

收到 SIGINT/SIGTERM（Ctrl+C）时取消全部超时上下文、等待日志落盘、发送中断告警后退出（码 130），不误报为业务错误。

3 安装与构建Install

源码构建（支持交叉编译）→ 放入 PATH 即可作为 kubectl 插件使用。

3.1 构建

# 默认：linux + 本机架构 → bin/kubectl-check
make build

# 交叉编译 Windows（自动加 .exe 与 os-arch 后缀）→ bin/kubectl-check-windows-<arch>.exe
make build GOOS=windows

# 交叉编译 macOS（可显式指定架构）
make build GOOS=darwin GOARCH=arm64

# 一次构建全部平台 / 安装到 GOBIN / 其他常用目标
make all
make install
make test      # 运行全部单元测试
  • 不指定参数时默认 linux + 本机架构，产物名保持 kubectl-check 不变；其他平台产物自动带 -<os>-<arch> 后缀，互不覆盖。
  • 依赖仅 github.com/spf13/cobra 与 k8s.io/client-go（版本见 go.mod），构建前可 make tidy 整理依赖。

3.2 作为 kubectl 插件安装

kubectl 会自动发现 PATH 中以 kubectl- 开头的可执行文件。将二进制命名为 kubectl-check 放入 PATH 即可：

# Linux / macOS
cp bin/kubectl-check /usr/local/bin/kubectl-check
kubectl check -h

# Windows：命名为 kubectl-check.exe 后放入 PATH

也可以直接以独立二进制运行：./kubectl-check -n delta deployment/my-app，效果完全一致。

4 快速开始Quick Start

三个最常见场景，复制即可用。

场景 A：发布后立刻检查（CICD 卡点）

# CICD 触发 rollout 后紧跟此命令：检查 delta 命名空间的 deployment/my-app
kubectl check -n delta deployment/my-app

Pod 全部就绪且无真错误 → 退出码 0；异常 → 告警 + 非零退出码，流水线据此决定是否卡点。

场景 B：自定义超时 + 飞书告警 + 错误日志落盘

kubectl check -n delta deployment/my-app \
  --pod-ready-timeout=300 --log-check-timeout=60 \
  --log-dump --log-error-dir=./errlogs \
  --feishu-webhook=https://open.feishu.cn/open-apis/bot/v2/hook/xxx \
  --feishu-secret=yyy

场景 C：监听模式（值守）

# 监听所有命名空间：Deployment 创建/更新自动检查（常驻，Ctrl+C 退出）
kubectl check -A

# 只监听 prod 后缀命名空间（支持逗号分隔多值与 * / ? 通配）
kubectl check -n '*-prod'
提示 资源参数支持 kubectl 两种风格：deployment/my-app 与 deployment my-app。当前仅支持 deployment 这一种资源类型。

5 两种运行模式Modes

带资源参数 = 单次检查；不带资源参数（配合 -A 或 -n）= 常驻监听。

单次检查模式

触发：手动执行 / CICD 流水线调用。

形式：kubectl check -n <ns> deployment/<name>

  • -n 须为精确单值（多值 / 通配符仅监听模式可用）
  • 未指定 -n 时默认 default
  • 执行一次完整三阶段检查后按聚合结果退出
监听模式（常驻）

触发：-A（全部命名空间）或 -n 过滤（逗号分隔多值 + */? 通配，如 '*-prod'、delta,gamma），不带资源参数。

  • 匹配命名空间的 Deployment 创建或更新（generation 递增）时自动执行单次检查逻辑
  • 纯 status 变化不触发（副本数上报、ready 更新等）；kubectl rollout restart 会触发（它修改模板使 generation 递增）
  • 同一 Deployment 相同 / 更小 generation 不重复触发；删除后同名重建（generation 重置）仍触发
  • 启动时已存在的存量 Deployment 不触发（避免 -A 启动瞬间对全集群扫一遍）
  • 每次检查在独立 goroutine 中运行，互不阻塞
  • Ctrl+C / SIGTERM：停止监听并中断全部进行中的检查（退出码 130）
注意 -A 模式下不可再带资源参数（会报错）；无资源参数且未给 -n 也会报错——工具会给出明确的用法提示（退出码 1）。

6 工作原理：三阶段检查How It Works

目标定位 →（阶段2 就绪等待 ∥ 阶段3 日志观察）→ 聚合退出。两阶段并行、独立超时、终态联动。

定

目标定位--pod-ready-timeout 窗口内

启动时定位本次发布（最新 ReplicaSet）的目标 Pod，不校验 Deployment 的滚动状态：

  • 发布刚触发、新 RS 的 Pod 尚未创建 → 在窗口内轮询等待出现，Pending 即算定位成功；
  • 滚动过程中陆续出现的新目标 Pod 会被自动补录纳入跟踪（上限为期望副本数，surge 超额副本不入名单）；补录的 Pod 仅做就绪检查（不启用日志观察），日志判定由定位时已存在的首发 Pod 承担——同版本 Pod 同镜像同配置，一个副本的日志即可代表本次发布；
  • 定位失败（replicas=0 无目标可等，或窗口内始终未出现）→ 发送告警后直接退出（码 2），不继续追踪。
2

阶段2：就绪等待--pod-ready-timeout（默认 300s）

  • 每个目标 Pod 各自独立起算就绪超时（先发现的先起算，后补录的不吃亏）；
  • 等待 Ready 条件（含就绪探针校验，等价 kubectl wait --for=condition=ready）；无探针容器 Running 即就绪；
  • 就绪超时 / 重启次数超过 --max-restart / 容器异常退出 → 置全局 pod failure → 告警 + 退出码 3；
  • 优先级：Pod 未就绪 > 日志报错（两害相权取其重，退出码跟随更严重者）。
3

阶段3：日志观察--log-check-timeout（默认 60s，从首次 Running 起算）

  • Pod 首次进入 Running 即启动（不等 Ready），follow 增量读取日志；
  • 有探针时 0/1 Running 期间两阶段共同作用，任一终态联动取消另一路（同一故障仅一条告警）；
  • 窗口结束无容器崩溃 → 正常退出；命中真错误仅发送提醒（不改变退出码，仍为 0）；
  • 容器异常退出（退出码 ≠ 0）不经仲裁、不受开关影响 → 退出码 3；Ready 前崩溃立即告警，不等就绪超时。
⇅ 阶段2 与 阶段3 并行执行，超时各自独立、互不挤占
终

聚合退出

等待全部 goroutine（含日志落盘）完成后，按全局状态聚合出最终退出码（见下节）；收到中断信号则优雅退出（码 130）。

后置补录说明 多副本滚动更新时，定位阶段通常只能见到部分新 Pod；发现器以 1 秒轮询 + 全量 List 快照的方式补录后续出现的 Pod，直到达到期望副本数。"两个 Pod 同时创建"等并发时序由轮询快照模型天然吸收，不会漏跟踪、也不会重复跟踪。

7 判定场景与退出码Scenarios & Exit Codes

三个判定场景 + 五个退出码，CICD 按退出码决定流水线行为。

7.1 三个判定场景

场景条件动作退出码
场景 1 全部正常 Pod 在超时内就绪，且无真错误日志 正常结束，无告警 0
场景 2 未就绪 Pod 超时未就绪（含探针失败）/ 重启超限 / 容器异常退出 发送告警，程序异常退出 3
场景 3 带病运行 Pod 已就绪，但日志存在真错误 发送提醒「xx pod 存在错误日志，但 pod 已就绪，需要检查」；--log-dump 开启时落盘。不中断 0

7.2 退出码总表

0
正常：场景1；或场景3（已就绪但存在真错误日志，已提醒）
1
参数解析错误、目标资源不存在
2
目标定位失败：replicas=0 无目标可等，或窗口内未出现目标 Pod（告警后直接退出，不继续追踪）
3
场景2：Pod 超时未就绪 / 重启超限 / 容器异常退出
130
收到中断信号（Ctrl+C / SIGINT / SIGTERM）主动退出
流水线建议 CICD 卡点可按 code != 0 判失败；若希望「带病运行」也算失败，需在脚本里额外解析场景3 的提醒输出（工具自身语义：就绪即不阻断）。

9 日志能力详解Logging

四个正交能力：控制台输出、关键字判定、LLM 仲裁、落盘——互相独立、可任意组合。

9.1 能力矩阵

能力开关默认说明
控制台实时输出--log-console开启追踪流读到的日志行逐行输出（原始行），效果同 kubectl logs --follow；与判定/落盘互不影响
错误关键字命中--keyword-check关闭关闭时 errorHit 恒为 false，场景3 提醒不触发；开启后由 --log-err-keywords 决定关键字
LLM 真伪仲裁--llm-enable关闭关闭时回退「关键字即真」；开启后只有真错误才提醒/落盘，假错误静默
错误日志落盘--log-dump关闭关闭时检测/告警/退出码均不受影响，仅不产生文件；开启后真错误/异常退出时写文件

9.2 判定链路

日志行按以下顺序流经判定链（每层可独立开关）：

follow 日志流 ──► --log-console 实时输出（旁路，不影响判定）
       │
       ▼
 ① 忽略关键字 --log-ignore-keywords 命中？ ──是──► 放行（不参与判定与标红）
       │否
       ▼
 ② 错误关键字 --log-err-keywords 命中？ ──否──► 正常行
       │是（需 --keyword-check 开启）
       ▼
 ③ LLM 仲裁 --llm-enable 开启？ ──否──► 关键字即真（默认路径）
       │是
       ▼
 ④ LLM 判定为真错误 ──是──► 场景3 提醒 +（--log-dump 开启时）落盘
       │否
       ▼
      假错误，静默（不告警、不落盘、不标红）
  • 不经仲裁的特例：容器异常退出（退出码 ≠ 0）无条件按失败处理，--log-dump 开启时无条件落盘保留现场（LLM 启用时同样全量快照）。
  • 优先级：Pod 未就绪（场景2）> 日志报错（场景3）。

9.3 常用组合速查

需求参数组合
只看就绪，不关心日志内容（最轻量）（默认即可，--log-console 开着也只是回显）

回显日志 + LLM 仲裁降误报 + 落盘--keyword-check --llm-enable --log-dump --log-error-dir=./errlogs

自定义关键字 + 忽略噪音--keyword-check --log-err-keywords=error,panic --log-ignore-keywords="level=debug"

10 LLM 日志错误仲裁LLM Arbitration

用大模型区分「真错误」与「关键字误报」，显著降低告警噪音。默认关闭，需 --keyword-check --llm-enable 同时开启。

10.1 工作方式

  • 命中错误关键字（且未被忽略关键字抵消）的日志行投入 Pod 级有界队列；
  • 异步攒批（10 行 / 2 秒）+ 相同行去重后，以 OpenAI 兼容协议调用 LLM 批量判定；system prompt 要求逐行返回 {"results":[{"is_error":true|false},...]}；
  • 任一真错误 → 发送场景3 提醒；--log-dump 开启时以容器启动时刻为起点（SinceTime）全量拉取该 Pod 各容器日志，覆盖写快照落盘，后续新真错误刷新快照；
  • 全部假错误 → 不告警、不落盘。

10.2 降级与熔断（可靠性设计）

情形行为
LLM 调用失败（超时 / 网络 / 解析失败）该批按「关键字即真」处理——宁误报不漏报
连续 3 次失败自动熔断：后续命中直接按关键字即真，不再发起网络调用
--llm-enable=false（默认）完整回退历史行为：--log-tail 回溯 + follow 增量；--log-dump 开启时首次命中落盘后追加

10.3 自建端点（敏感日志不出内网）

kubectl check -n delta deployment/my-app --keyword-check --llm-enable \
  --llm-endpoint=http://llm.internal:8000/v1/chat/completions \
  --llm-model=my-model --llm-api-key=xxx

判定协议为 OpenAI 兼容（/v1/chat/completions），任何兼容网关（vLLM、OneAPI 等）均可接入。默认端点为智谱 GLM。

安全提示
  • 默认 API Key 内置于源码（internal/llm 常量）：仓库若公开有泄露风险，请用 --llm-api-key 覆盖，并到智谱控制台轮换内置 key。
  • 日志内容会发送至 LLM 端点（默认为云端）：敏感日志场景请将 --llm-endpoint 指向内网自建的 OpenAI 兼容端点。
  • API Key 仅出现在请求头，不会写入任何日志输出或落盘文件。

11 错误日志落盘Log Dump

--log-dump 开启后，命中真错误 / 容器异常退出时保留日志现场，供事后排查。默认关闭。

11.1 文件规则

  • 文件命名：{namespace}-{podName}-{date}.log（date 格式 20060102，跨天自动切换文件）；
  • 目录由 --log-error-dir 指定（默认当前目录 .）；
  • 错误行用 ANSI 红色转义码标注，忽略规则命中的行不标红；
  • 关闭 --log-dump 时：检测、仲裁、告警、退出码均不受影响，仅不产生文件。

11.2 两条落盘路径

路径机制特点
LLM 启用
--llm-enable		 确认真错误后，以容器启动时刻为起点（State.Running.StartedAt；已退出取 LastTerminationState；均不可得回退 Pod 创建时间）从 K8s API 全量拉取从启动到当前的日志 覆盖写整份快照；新真错误刷新快照——文件始终是"从容器启动至今"的完整现场
LLM 禁用（默认） follow 流带 --log-tail 行回溯；命中关键字前缓冲在内存环形缓冲，首次命中把「回溯行 + 命中行」落盘，此后增量追加 同日同 Pod 追加同一文件；无额外 API 拉取开销
建议 生产环境推荐 --log-dump --log-error-dir 指向独立目录（如 ./errlogs），配合场景2/3 告警中的落盘路径提示，可在告警到达时直接定位现场文件。

12 飞书告警Feishu Alert

告警优先发飞书 interactive 卡片；未配置 Webhook 时自动降级控制台输出，告警事件从不静默丢弃。

12.1 配置

kubectl check -n delta deployment/my-app \
  --feishu-webhook=https://open.feishu.cn/open-apis/bot/v2/hook/xxx \
  --feishu-secret=yyy          # 机器人开启了签名校验时填写（HMAC-SHA256）
  • --feishu-webhook 非空即启用飞书告警；为空（默认）时所有告警降级打印到控制台；
  • 发送为非阻塞模式：告警发送失败或超时不影响检查流程与退出码；
  • --feishu-dedup-window（默认 30 秒）：同 Pod + 同事件在窗口内只告警一次，防止滚动期间重复轰炸。

12.2 告警事件一览

事件触发时机级别
目标未找到定位失败（replicas=0 / 窗口内无目标 Pod）阻断 退出码 2
Pod 未就绪阶段2 就绪超时（含探针失败）阻断 退出码 3
容器异常退出容器退出码 ≠ 0（Ready 前崩溃立即告警，不等就绪超时）阻断 退出码 3
重启超限重启次数超过 --max-restart阻断 退出码 3
存在错误日志场景3：已就绪但存在真错误（提醒，不阻断）提醒 退出码 0
监听模式启动 / 触发监听启动、Deployment 创建/更新触发检查（控制台 INFO）信息
中断收到 SIGINT/SIGTERM（发送中断告警后退出）中断 退出码 130

13 防误报与可靠性设计Anti-false-positive

发布现场噪声多，工具内置多层防误报机制。

机制解决的问题
Terminating Pod 不计异常滚动更新时 controller 删除中的 Pod（surge 缩容 / 回滚）phase 可能仍是 Running，若计入会误报——统一过滤（DeletionTimestamp 非空的 Pod 跳过）
忽略关键字抵消--log-ignore-keywords 命中的行不参与判定、不标红（如 level=debug 里的 "error" 字样）
LLM 真伪仲裁关键字命中后由 LLM 判定真伪，假错误静默——只有真错误才提醒/落盘
两阶段终态联动阶段2/3 任一出终态即取消另一路，同一故障仅一条告警，不重复轰炸
告警去重窗口同 Pod + 同事件 30 秒内只告警一次
surge 副本不入名单后置补录上限 = 期望副本数，滚动期间的超额临时副本不纳入跟踪，避免把"将被删除的 Pod"当成异常
LLM 失败降级 + 熔断LLM 不可用时回退「关键字即真」（宁误报不漏报），连续失败熔断避免拖慢检查
优雅中断Ctrl+C / SIGTERM 等待日志落盘后以码 130 退出，不误报为业务错误，CICD 可区分「人主动取消」与「检查失败」

14 常见问题 FAQTroubleshooting

按现象速查。排查时建议先加 -v 查看详细过程。

退出码 2（目标定位失败）是怎么回事？
两种可能：① 目标 Deployment replicas=0，无目标可等；② 发布刚触发但新 RS 的 Pod 在 --pod-ready-timeout 窗口内始终未创建出来（如镜像拉取卡住、调度资源不足）。可加大 --pod-ready-timeout 或先排查 kubectl get rs 确认新 RS 是否产生 Pod。
明明日志里有 error，为什么没有任何提醒？
日志内容判定默认全部关闭。需要显式开启：--keyword-check（关键字命中），需要 LLM 仲裁再加 --llm-enable。另外检查是否被 --log-ignore-keywords 抵消、以及 LLM 是否判为假错误（假错误静默是设计行为）。
Pod 已就绪但日志有真错误，为什么不阻断（退出码还是 0）？
这是场景3 的设计语义：就绪即放行，仅发送提醒「xx pod 存在错误日志，但 pod 已就绪，需要检查」，不改变退出码。若流水线需要卡点，需自行解析提醒输出。
为什么有些 Pod 没有被日志跟踪？
多副本滚动时，只有定位阶段已存在的首发 Pod 做完整检查（就绪 + 日志）；后置补录的 Pod 仅做就绪检查。同版本 Pod 同镜像同配置，一个副本的日志即可代表本次发布内容，这样也避免了 N 倍的 API 连接与 LLM 成本。后置 Pod 的故障由就绪超时兜底。
飞书收不到告警？
① --feishu-webhook 是否非空（为空时降级控制台，去终端输出里找）；② 机器人若开启了签名校验，必须同时配置 --feishu-secret；③ 30 秒去重窗口内同事件只发一次；④ 告警为非阻塞发送，检查网络连通性。
监听模式下为什么我改了 Deployment 却没触发检查？
只有 spec 变化（generation 递增）才触发：纯 status 更新（副本数上报、ready 数变化）不触发；启动时已存在的存量 Deployment 不触发；同一 generation 重复更新不触发。用 kubectl rollout restart 或改镜像/模板即可触发。
落盘文件里为什么有乱码一样的字符？
错误行带有 ANSI 红色转义码（便于 cat/less -R 时直接标红显示）。用支持 ANSI 的查看器打开即可。
如何减少 LLM 成本 / 让日志不出内网？
将 --llm-endpoint 指向内网自建的 OpenAI 兼容端点（vLLM / OneAPI 等），并用 --llm-model 指定自部署模型；或干脆关闭 LLM（--llm-enable=false）回到关键字即真的零成本路径。
CICD 里怎么区分「用户取消」和「检查失败」？
退出码 130 = 收到 SIGINT/SIGTERM 的主动退出；3 = 检查失败；2 = 目标定位失败。脚本按 $? 分支处理即可。
